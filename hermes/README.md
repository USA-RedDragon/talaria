# Talaria Hermes (`hermes/`)

A small set of patches on top of the pinned [Hermes Agent](https://github.com/NousResearch/hermes-agent) release, built into a multi-arch image (`linux/amd64`, `linux/arm64`, the same platforms as upstream's image). The image is published publicly as **Talaria Hermes**, `ghcr.io/usa-reddragon/talaria-hermes`.

Built on Hermes Agent by Nous Research (MIT). Not affiliated with or endorsed by Nous Research.

Hermes Agent is Copyright (c) 2025 Nous Research, under the MIT License in [LICENSE](LICENSE); the patches use the same terms. The image carries both files in `/usr/share/doc/talaria-hermes/` (`LICENSE`, `NOTICE`).

Each patch fixes one limit, sits behind a config option whose default keeps upstream's behavior, has upstream-style tests, and is written so that upstream can take it. When upstream ships a fix, the patch is dropped.

## How it works

- `Dockerfile` starts from `docker.io/nousresearch/hermes-agent:<release>@<digest>` (`ARG HERMES_BASE`), and sets `HERMES_BASE_IMAGE` to that reference in the image. A build stage on the build platform applies `patches/*.patch` in name order to the source in `/opt/hermes` with `scripts/apply-patches.sh --image`, and the final stage copies only the changed files on top of the upstream image. Nothing runs on the target platform, so the arm64 image needs no emulation. Hunks for files that are not in the image (tests, docs) are skipped there.
- New layers are zstd. The upstream layers keep their compression and digests, so nodes reuse the layers they already have from the upstream image and a release adds only the patched files.
- The Hermes version that the image reports is upstream's, so tools that check the Hermes version see the base release.

## Releases and tags

Image tags are `v<upstream release>-p<n>`: `v0.23.1-p1`, `v0.23.1-p2`, then `v0.24.0-p1` after the base moves. The upstream release is always the part before `-p`. In this repository the git tag and GitHub release of each image are `hermes/v<upstream release>-p<n>` (bare `v*` tags are talaria daemon releases). Releases up to `v0.23.1-p31` were made before the move into this repository; their tags were carried over with the `hermes/` prefix, and their signatures name the old repository, so verify them with `--certificate-identity-regexp '^https://github.com/USA-RedDragon/'`.

The Hermes release workflow (`.github/workflows/hermes-release.yaml`) runs on every push to `main` that changes `hermes/Dockerfile`, `hermes/patches`, `hermes/scripts` or the Hermes workflows. It runs the tests, then builds and pushes `ghcr.io/usa-reddragon/talaria-hermes:<tag>` (also tagged `latest-stable`), with BuildKit SLSA provenance and an SBOM, signs the image keyless with cosign (GitHub artifact attestations are not available for private repositories of a user account), and creates the tag and a GitHub release that lists the patches (never marked latest, so the talaria daemon's release stays latest). Run it by hand (workflow_dispatch) for a dry run that prints the next tag and builds without pushing; with `publish` on it releases HEAD again.

Verify a release with `cosign verify ghcr.io/usa-reddragon/talaria-hermes:<tag> --certificate-identity-regexp '^https://github.com/USA-RedDragon/talaria/' --certificate-oidc-issuer https://token.actions.githubusercontent.com`.

Renovate bumps `HERMES_BASE` in the Dockerfile as soon as upstream releases. A green PR merges on its own, which publishes `v<new release>-p1`. Rolling it out is a separate Renovate PR in the Flux repo that is never merged on its own.

## CI

The Hermes test workflow (`.github/workflows/hermes-test.yaml`) runs on pull requests and before each release:

- **Patches**: clones upstream at the release in the Dockerfile, applies every patch to the full tree, installs the locked test environment with uv, and runs each patch's tests. A patch that no longer applies fails with `<patch> does not apply to Hermes <release>`. A patch's tests are the test files it adds or changes plus the files in `patches/<name>.tests`.
- **Hub contract**: the contract tests of the hub in `hub/` (`TestContractAgainstSource`, `TestClientMethodsAgainstSource`) against the patched tree, with `HERMES_AGENT_VERSION` set to the upstream release.
- **Image**: builds the image for both platforms, then runs the device plugin tests (`plugin/` at the repository root) inside the amd64 image.

## Adding or changing a patch

1. Clone upstream and check out the release in the Dockerfile. Commit there as `USA-RedDragon <USA-RedDragon@users.noreply.github.com>` (`git config user.name USA-RedDragon`, `git config user.email USA-RedDragon@users.noreply.github.com` in that clone): the patch headers are public, and the Patches check fails on any other author.
2. Make the change as one commit with its tests, in upstream's style and with a config option that keeps upstream's default.
3. Run its tests: `uv sync --locked --python 3.14 --extra all --extra anthropic --group dev --group test`, then `.venv/bin/python -m pytest <test files>`.
4. Put all patches on one branch in order and export them: `git format-patch --zero-commit --no-signature -o patches <release>..HEAD`. Keep the numbers in the file names; they set the order.
5. List neighboring upstream tests the patch must keep green in `patches/<name>.tests`.
6. Add the patch to the table above.

## Rebasing

When a Renovate PR fails in "Patches" with `does not apply`:

1. Clone upstream at the new release and `git am -3 patches/*.patch`.
2. Resolve each conflict, run the tests, and export again as in step 4 above.
3. If upstream now has the fix, delete the patch, its `.tests` file and its row in the table.
4. Push to the Renovate branch. CI runs again.

## Upstream branches

`upstream/<name>/` holds each patch ported to upstream `main`, as `git format-patch` output with the upstream commit it applies to (`BASE`) and a pull request description (`PR.md`). Apply with `git am` on that commit to get a branch ready for a pull request.
