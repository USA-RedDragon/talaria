# Subagents, agent messages and goals

A chat can hand work to subagents, message other chats, and keep working on a goal for hours. This page covers what the hub shows and enforces for each: the subagent rows in Activity, subagents that wait on a background job, resuming a finished subagent, subagent questions that go to the parent chat, the model routes of subagents, messages between agents, running several lanes at once, and goals.

Where this page says "Talaria Hermes", it means the patched Hermes image (see [Talaria Hermes patches](../../hermes/README.md)); the patch numbers are the ones in that table. Approvals that subagents raise are in [Approvals and trust](approvals-and-trust.md).

## Subagents in Activity

**Subagents** are the children that `delegate_task` starts. The page builds each row from the session's `subagent.spawn_requested`, `subagent.start`, `subagent.thinking`, `subagent.tool`, `subagent.progress` and `subagent.complete` events, and from `GET /api/sessions/<backend>/<session>/activity`, which reads `subagent.list`, `process.list` and `delegation.status`, every 3 seconds while the sidebar is open or anything runs (every 10 seconds when the event feed has carried subagent events in the last 15 seconds and no background command runs) and every 20 seconds otherwise. A child shows under the subagent that started it. An open row shows the subagent's steps as a small chat: its text as replies, its thinking folded, its tool calls as the chat's tool cards folded into the chat's groups (a running call with its spinner, a failed one red with how long it ran), the messages you sent it, and a Done or Failed card at the end. It follows new steps while you are at its end; scrolled up, it stays put and a pill counts the new steps. A finished row keeps its steps, and "Open full transcript" shows them all. The page reads them from `GET /api/sessions/<backend>/<session>/subagents/<id>/events?after=<seq>`, which answers typed events (`seq`, `ts`, `type`: `goal`, `user`, `message`, `thinking`, `tool_start`, `tool_end`, `steer` or `compaction`, and `call_id`, `name`, `args`, `result` cut to 8,192 characters with `result_size`, `duration_ms`, `error`, `text`) after that seq, at most 500 at a time (`more` says there are more), with `epoch`, which changes when Hermes rewrote the transcript and the page reads it again from the start. The hub reads the child's stored transcript (`session.transcript` with `subagent_id`) into its database before it answers, so the steps stay after the subagent ends; when Hermes cannot answer, the stored steps answer (`live: false`). Tool results and the calls of a step without text need Talaria Hermes (`tool_details`, `runtime.describe` lists `transcript-tool-details-v1`; `details` in the answer); without it a call shows without its output. How long a call ran comes from Hermes when `sessions.tool_outcome_metadata` is on (Talaria Hermes, patch `0053`; `false` turns it off), and is the time between the call and its result otherwise. A user reads only their own copy, of a chat on a backend they may use; the hub drops a subagent's steps 90 days after it last read new ones. "Message this subagent" queues text that the subagent reads at its next step (`subagent.steer`); the hub keeps it with the time you sent it and shows it as waiting until a tool result comes after it, since Hermes hands it over with the next tool result, and then as read. Stop interrupts it (`subagent.interrupt`). Pause and Resume set Hermes's switch for new subagents (`delegation.pause`): it covers every chat of the backend, and subagents that run go on. An approval that a subagent raises names the subagent in the chat (see [below](#questions-and-approvals-go-to-the-parent-chat)); the hub shows it in the subagent's row only when the command matches that subagent's last tool call (`last_preview` of `subagent.list`) or only one subagent runs, and the chat shows it in every case.

### Waiting on a background job

A subagent with a job that runs for hours does not have to poll. With `process_manage` handoff and `resume_on_exit=true`, the process stays the subagent's, the subagent ends its turn, and its unit stays open (patch `0092`). The row shows **Waiting**, with the first command it waits on and how many more (`Waiting on make all (+1 more)`), counts as running, and is not marked done. When a watched process exits, the subagent continues its conversation with the exit code and the output tail. After `delegation.max_wait_hours` (24) it is resumed with a timeout notice. The parent gets one result, when the subagent really finishes. Handing off the same command again returns the first watch, and a subagent holds at most eight. A restart hands the waiting subagent to the next gateway with its watches, which reattaches the processes and goes on waiting.

### Resume a finished subagent

A finished background subagent can take a second round of work with its full context, instead of a new subagent briefed from notes. `delegate_task` with `action='resume'` (a `subagent_id`, or `delegation_id` and `task_index`, and a `message`) rebuilds the child from its stored transcript: same goal, route and model, toolsets, working directory and device binding, with its original start time and tool count carried on. The message becomes the next user turn, the child runs as a new background unit, and its result comes back as `Subagent resumed and finished: ...` in the same notice card as any subagent result (see [Notices from Hermes](../../hub/README.md#notices-from-hermes)). The unit counts toward the chat's cap and queues behind it, approvals and questions go to the parent chat, and a restart hands it off like any other. Hermes refuses a resume of a child that still runs or is queued (steer it instead), of another chat's child, from a nested subagent, and of a child with no finished-run record (one spawned before patch `0087`, or under worktree isolation). The record lasts as long as the session: `sessions.retention_days` (90) when `sessions.auto_prune` is on, otherwise until the parent chat is deleted. The `delegation_id` lookup also needs the delegation's manifest in the live-log directory, which Hermes cleans up after 7 days (patch `0055`); the `subagent_id` does not.

### Questions and approvals go to the parent chat

A background subagent that needs an approval (patch `0080`) or has a question (`clarify`, patch `0088`) asks in the chat that started it. The card reads `Subagent "<goal>" asks: ...` and the pending prompt carries a `subagent` field, so the page, Telegram and the other viewers show it as they show the chat's own prompts. It arrives as an ordinary approval or question of the chat, so the notices and reminders for those cover it (see [Notifications](../../hub/README.md#notifications)). It waits as long as a chat prompt does (`approvals.timeout` for an approval, `agent.clarify_timeout` for a question), and on silence the subagent gets the usual timed-out reply.

The prompt belongs to the chat, not to the turn that started the subagent. The turn's end keeps it while the chat has live subagents, an answer from a later turn or from an idle chat reaches the subagent (an idle chat with such a prompt reads as waiting), and a typed message answers a question only while it waits for free text, so a message meant for the idle chat never cancels a choice card. A subagent can ask even after its parent chat left the gateway's memory: Hermes restores the retired conversation, or, when it cannot, still shows the card through the chat adapter (patch `0104`). A child that raises an error reports its exception type, message and place, not a bare key.

A child that an orchestrator joins inline, a session that joins its children (`delegation.gateway_mode` inline), a parent without `clarify` and a chat with no way to show a question keep the old behavior: the child has no `clarify`.

Your answer to a subagent's question counts as your words for the approval review, and covers that subagent's next command; see [Approvals and trust](approvals-and-trust.md#your-answers-to-questions-count).

### How many run at once

With `delegation.at_capacity: queue` (the default in Talaria Hermes, patch `0064`), `delegation.max_concurrent_children` caps each chat's own background subagents and `delegation.max_concurrent_children_total` the whole process (0 means no cap). A call over a cap returns at once as queued, and starts when a slot frees, oldest first. The row shows it as **Starting**; a steer joins its goal when it starts, and Stop settles it without running.

## Subagent routes

The Subagents picker beside Model and Thinking sets which models the chat's subagents (`delegate_task`) may use. The chat's own model stays the orchestrator. The choices come from the backend's subagent-routes Hermes plugin, which provides the `model_map` delegation backend with the routes of `delegation.backends.model_map.options` in Hermes's config:

- **Auto (model chooses)**: the model picks a route for each subagent by the routes' descriptions.
- **Every subagent on** a route, named by its route title: every subagent runs on that route, whatever the model asks for.
- **Ask for help**, shown as `<route title> when stuck`: subagents run on the chat's own model, and the model may start one subagent at a time on the stronger route. A second one while the first runs or starts is refused, and so is any other route.
- **No subagents**: every subagent is refused.

The line under the pickers says what the choice means. The choice belongs to the chat and follows it across context compression; the next subagent takes it. Each turn of a chat with a choice tells the model the rule in one line. `/model` in Telegram shows the choice with a button for each one. The hub calls `GET` and `PUT /api/plugins/subagent-routes/sessions/{session}` (`{"choice"}`) with its dashboard login; its own route is `GET` and `PUT /api/sessions/<backend>/<session>/subagents`. A backend whose Hermes answers 404 has no plugin, and the hub shows no picker for it.

## Agent messages

The user's agents can message each other through the hub, as Claude Code sessions do: a chat, or a subagent that a chat delegated to, lists its peers and sends one of them a message, and the target can answer the same way. It does not matter which computer each chat runs its commands on: a message goes from Hermes to the hub and back to Hermes, never through a device. The agent's tools come from the talaria device plugin (`agent_peers`, `agent_send`, `agent_set_name`, talaria docs/protocol.md section 12). The hub takes their calls from the plugin with a long poll (`GET /api/plugins/device/agents/requests`, with the hub's dashboard login), so Hermes needs no way to reach the hub.

- **Scope.** An agent reaches only the chats of its own backend and the subagents of its own delegation tree. Each person has their own backend, so one person's agents never reach another person's. A backend with devices has agent messages on when `backends[].users` names exactly one user and `groups` is empty. A backend that several people share needs `backends[].agent_messages: true`: Hermes does not record which person a chat belongs to, so all its chats then count as one person's, which they already are to the hub (every user of a backend sees and drives every chat on it). `agent_messages: false` turns it off. Only chats of the hub, an editor or the terminal count (session source `gui`, `local`, `cli`, `tui`, `acp` or `desktop`): conversations that Hermes holds itself on a messaging platform, such as a Telegram group, may have other people in them, so agents never see or reach them. The router polls a backend's plugin only when the plugin's `backend_id` is that backend's id.
- **Addressing.** `to` is a session id, a chat's short name (`agent_set_name`, unique per backend), an exact chat title, a subagent id (`sa-...`) or `parent`. A session id always wins. A name may not equal another chat's id or title, and a name of one chat that equals the title of another is refused as ambiguous, so a chat cannot take another chat's messages by its name. `agent_peers` shows each chat's id, name, title, computer and folder (or the sandbox or the Hermes server) and whether a turn runs, running chats first, then live ones, then newest first, at most 30, without archived chats and chats older than 7 days that are not live.
- **Delivery.** A message to another chat is a new input of that chat (`prompt.submit` under the submission id `hermes-hub-agent-<id>`): an idle chat starts a turn. A busy chat takes it as Hermes's steer, as it takes a user's text typed mid-turn (`prompt.steer_queued`): it reads the message with its next tool result, under the same header, and the page shows the agent-message card at that point. When Hermes refuses the steer (the turn is ending or has no agent yet), the message stays the chat's next input and runs after the turn. `agent_send` says which happened: "started a turn", "steered into its running turn" or "queued for when its turn ends". A parent's message to its own running subagent is Hermes's steer, which the child reads after its current step. A subagent's message to its parent, or to a sibling, rides on the target's next tool result while the target runs; a parent chat whose turn does not run, or ends before it reads the message, gets it as a new input. A chat that runs on someone's computer runs what the message leads to with that chat's own binding and approvals, never the sender's. The hub refuses to deliver an input to a chat in yolo mode (`config.get` `yolo`), since what the message leads to would then run with no approval the user sees; a chat whose mode it cannot read is refused too.
- **Marking.** The target gets the first line `[Agent message am_<id> from <sender>]` and a paragraph that says another agent wrote it, not the user, that it is not the user's instruction or approval, and that a reply in its own chat does not reach the sender, so an answer goes through `agent_send`. The page shows such a message as a notice card "Message from ..." (see [Notices from Hermes](../../hub/README.md#notices-from-hermes)) and the sender's `agent_send` call as a tool card "Sent a message to ...", so the traffic shows in both chats. The Telegram bot sends an incoming agent message to the Telegram chats attached to the target. The hub drops control and format characters (zero-width and bidi ones too), turns `@file:`-style references into a full-width `＠`, so the text cannot read files into the target's context, and turns each `[` that could open a frame marker (one that no word character or closing bracket precedes and a letter or `/` follows, such as `[OUT-OF-BAND USER MESSAGE`, `[System note:` or `[Agent message`) into a full-width `［`, so the text cannot fake the end of its frame or a note from Hermes. Devices may not submit inputs under `hermes-hub-` submission ids.
- **Approvals.** A message is text in the target's context. The header says it is not the user's instruction or approval, and the hub never answers an approval for the target. Approval prompts of a turn that a message started go to the user as always. A model can still follow what a message says; the frame tells it not to take the text as the user's words, but the target's approvals are the boundary. The hub checks only the chat's own yolo switch and refuses delivery to a chat in that mode.
- **Limits.** A message, a chat tree, a pair of chats, a backend and a back-and-forth chain each have a limit, with a higher one for the chats of one delegation tree and for chats the user marked as working together. The numbers are kept next to the code they come from, in [Agent message limits](../../hub/README.md#agent-message-limits).
- **Scheduled jobs.** A cron job can send agent messages: the device plugin adds `device-agents` to the job's `enabled_toolsets` unless the list is empty (`[]`) or the plugin setting `cron_agents` is `false`. The sender reads "cron job '<name>' (id <job id>)" in the header (`cron job <job id>` when the job has no name). The limits count one job as one sender across all its runs, and its messages carry no reply instruction, because a finished run cannot read an answer; a chat that does call `agent_send` to the run's session gets `unknown_peer`.
- **Record.** The hub keeps every message (sender, target, hop, text, how it was delivered) in its store for 30 days and logs each one as `agent message` without its text.

## Running several lanes

A lane is one delegated task: a subagent with its own goal, or a chat that works on its own part. A few rules keep several lanes manageable:

- **Give each lane its own goal and its own files.** The subagent starts with only what the goal says. Tell it which paths it owns and what "done" means.
- **Watch them in Activity.** Each lane has a row with its model, its steps and, when it needs you, a "Needs you" or "Waiting for your approval" state. A lane that waits on a long job shows **Waiting**.
- **Steer or stop.** "Message this subagent" reaches it at its next step; Stop interrupts it. A parent's message to its running subagent is the same steer.
- **Let them talk.** `agent_peers` lists the other chats and the subagents of the same delegation tree, with their relation (parent, child, sibling, same delegation tree). Messages inside one tree may chain up to 100 hops and count toward none of the other limits; messages to other chats keep the [limits](../../hub/README.md#agent-message-limits). Mark two chats as working together to give them more room.
- **Results come back as cards.** A finished lane shows as a "Subagent finished" or "Subagent failed" card in the parent chat, or one "N subagents finished" card for a batch. If nobody has the parent chat open when a lane finishes, Hermes can start a turn for the result instead of leaving a note (`sessions.unviewed_completion_turns`, patch `0007`, off by default).
- **A restart does not lose them.** With `delegation.restart_handoff` (off in the patch's defaults; the Helm chart and compose init files turn it on) a restart stops each background subagent at a clean point and the next gateway resumes it from its transcript.
- **Cap the parallelism.** Use the per-chat cap above.

## Goals

A `/goal` keeps a chat working until it is done. The command is Hermes's; it shows in the message box's `/` list when Hermes offers it for the chat. In Talaria Hermes (patch `0089`) a goal has **no turn cap** by default (`goals.max_turns: 0`; upstream stops at 20). It runs until the judge says it is done, you pause or clear it, or it is stuck.

- **Stuck pauses it.** A goal pauses by itself when the judge's "not done" reason repeats (reworded repeats count), or when a turn with no tool call repeats the previous reply, `goals.stuck_turns` turns in a row (default 3, 0 turns it off). The pause says why and points at `/goal resume`, which also clears the streaks.
- **A positive `goals.max_turns` still caps** the goal at that many turns and pauses it there.
- **Status** shows `turn N`, without a budget.
- **A restart does not end it.** A watcher (patch `0074`) queues one continuation for each active goal whose chat has been idle for 30 seconds with no running turn, queued input or pending admission. Paused, done and waiting goals stay as they are.

## Project memory and project skills

A chat in a git repository has project memory (the notes of the `project-memory` plugin) and project skills (patch `0094`). Both belong to the project, not to one chat, so the chat's subagents read them too: a project's skills directory is a skill root for the chat and its subagents, listed, loaded and edited only there, marked "project", and winning over a global skill of the same name. In a chat with a project, `skill_manage` must name a scope when it creates a skill: `project` for what is true of this codebase, `global` for a procedure that applies everywhere. The Memory page shows a project's notes and its skills, marked "project" (see [Memory](../../hub/README.md#memory)).

The notes are in the agent's system prompt up to the plugin's `char_limit`. Hermes cut every plugin section at 4,000 characters; patch `0091` adds `plugins.max_section_chars` (default 4000, at most 200000) for the largest section a plugin may ask for. project-memory asks for its `char_limit` plus a short header, so for `char_limit: 8000` set `plugins.max_section_chars` to 9000 or more. All sections together may use that value plus 4,000. Without the patch, or with the key unset, notes show up to 4,000 characters.
